# 使用说明（人与 AI 共用）

> 这份手册写给**两种读者**：第一次打开面板的人，和第一次调用这套工具的 AI。
>
> - **人**：从 §1 看到 §4 就能上手；§8 排障手册是出问题时最先翻的。
> - **AI**：§5（工具用法）、§7（数据在哪）、§8（症状→动作）是必须读的；每节的标题就是锚点，可以直接引用 `docs/manual.md#门禁` 这种链接。
> - **改代码的人**：去 [`AGENTS.md`](../AGENTS.md)，那里是开发约定；这份手册只管「怎么用」。

---

## §1 一分钟看懂

**它是什么**：一块挂在 DSH 里的「需求 → 任务」工作台。左边是看板，右边是设置；每条需求拆成卡，每张卡按列流转，每一列由某个角色的 AI 专家接手干活，人负责定方向和验收。

**它解决什么**：

- 需求不再是一句话丢过来 → 必须先答「澄清三问」、评审通过，才能拆成能开工的卡。
- 每张卡**卡的验收清单 = 需求的验收条件**，不是模板（唯一例外：澄清卡固定多一条「已检索历史结论」，没检索并留痕就过不了准出闸门）。
- AI 干完活要留证据（评论、交付物、执行记录、用例、代码事实），**没证据推不动**。
- 交付物自动落飞书云盘，按「项目 / 需求 / 类型」归档。

**它不是什么**：不是代码托管、不是 CI、不是 IM。它调用 GitLab / 飞书，但不管它们本身。

## §2 对象与关系

```
项目 Project ──┬── 需求 Requirement ──┬── 功能点 Point（带验收条件 acceptance）
               │                      ├── 卡 Task（一个功能点一张卡；卡的验收清单 = 功能点的 acceptance）
               │                      ├── 需求文档 Doc（PRD 基线）
               │                      └── 云盘目录 Folder（项目目录下的需求目录）
               ├── 迭代 Iteration
               └── 版本 Release ──── 挂一批卡，过门禁才发得出去

卡 Task ──┬── 评论 Comment（含 @专家 派活）
          ├── 交接契约 Handoff（决策 / 假设 / 未决 / 风险 / 影响面；派单提示词先读它，再看评论）
          ├── 验收清单 Checklist（"做完"的定义）
          ├── 测试用例 Case（接口/shell/浏览器/数据库；可归功能点 + 验收条件）
          ├── 交付物 Artifact（需求说明/设计/用例集/报告/MR…，正文进云盘）
          ├── 执行记录 Coding（agent、分支、commits、改动文件、单测结果、评审结论）
          └── 历史 History（谁在什么时候把它推到哪一列、为什么被拦）

专家 Expert / 专家团 Team ── 每个角色（产品/架构/研发/测试）一个 AI，派单后在自己的会话里干活
技能 Skill ── 可复用的做法（命令、坑、检查清单），派单时注入给专家
```

**一句话记法**：需求是锚点，功能点是可验收的最小单位，卡是能派单的工作单元，用例和交付物是证据。

**编号规则**（`src/host/task-code.js`）：

| 对象 | 编号 | 说明 |
| --- | --- | --- |
| 需求 | `REQ-2026-003` | 按年递增 |
| 需求卡（拆卡产物） | `REQ-2026-003-01` | 需求编号 + 需求内两位序号；卡号自带需求归属，同一需求的多张卡不再同名 |
| 其它卡 | `DEV-001` / `TEST-001` / `BUG-001` / `DES-001` / `OPS-001` | 按类型在**同一需求内**各自递增（不全局唯一） |
| 没挂需求的卡 | 无编号 | 挂上需求后自动补号 |

卡面上显示的是卡编号；所属需求的**编号与名称**在卡详情「其它信息 → 所属需求」（`REQ-2026-003｜需求标题`）、卡面紫色 chip 的悬停提示、以及导出的 CSV 里都能看到。老库升级时（`config.schema` 9）会把需求卡从「等于需求编号 / 老的 REQ-001」一次性迁成 `需求编号-NN`，幂等。

**两套交付物模型的分工**（issue #129）：`requirement.docs` 是**需求级文档**（PRD / 原型 / 验收标准，有版本与基线，显示在需求页）；`task.artifacts` 是**卡级交付物**（方案 / MR / 用例集 / 报告 / 原型，会归档到云盘、按类型进子目录）。问「这条需求交付齐了吗」时把两者合起来看：矩阵与准出的交付物数量已经把 `docs` 算进去了。

## §3 一条需求的完整旅程（人视角）

| 步 | 在哪做 | 做什么 | 不做会怎样 |
| --- | --- | --- | --- |
| 1 | 设置 → 项目与迭代 | 建项目（`KEY` + 名称 + 本地 git 路径） | 需求落不进项目目录，云盘只能进「未归属项目」 |
| 2 | 需求页 →「＋ 新建」 | 写需求：背景/目标/范围/**不做**/验收/风险六段 | 一句话需求拆出来全是没法验收的卡 |
| 3 | 需求详情 → 澄清三问 | 答「有没有服务端 / 谁做鉴权 / 交付边界」 | **拆卡会被拦**（`拆卡前先把澄清答完：…`） |
| 4 | 需求详情 → 功能点 / 可追溯矩阵 | 每个功能点写 1–3 条 `acceptance`；矩阵里点「编辑」在**表格上方就地表单**改（不跳页），勾选多个功能点可**批量替换验收条件**（一行一条，id 按位置复用，删掉的条件上的用例会变成「未挂条件」） | 拆出来的卡清单是空的，验收无从谈起 |
| 5 | 需求详情 → 评审 | 提交 → 通过 | 没评审通过**不能拆卡** |
| 6 | 需求详情 →「拆卡」 | 一个功能点变一张卡，落在「待澄清」 | — |
| 7 | 看板 | 卡片逐列流转；每列负责人（AI）会被派单 | 卡停在原地不动（看板顶部会提示「停摆」） |
| 8 | 验收 | 勾清单 → 签字 → 推到「已完成」→ 需求签字 | 需求永远停在「进行中」，版本也发不出去 |

**拖卡就够了吗？** 拖动 = 改状态，会自动检查该列的门禁；被拦时卡留在原列，历史里写清原因。绕过要显式 `override` 写理由（会计入 override 统计）。

## §4 门禁到底在拦什么 {#门禁}

六道门，**默认都开**（两道闸门可在「设置 → 列的负责人」里关，关了会在卡历史里留痕）：

| 门 | 什么时候拦 | 拦的条件 | 怎么过 |
| --- | --- | --- | --- |
| **澄清门禁** | 拆卡时 | 三问没答完 | 答完三问（`discovery`） |
| **拆卡闸门** | 拆卡时 | 有功能点没有**可判定的验收条件**（空数组或只有「体验良好」） | 用 `points[].acceptance` 补上；确实不适用可在「设置 → 列的负责人」关掉「拆卡验收条件闸门」（`config.requirementGate.requireAcceptance=false`） |
| **设计闸门** | 卡进「开发中」 | 没有设计记录，或评审未通过，或多稿未定案，**或评审人就是稿子的作者（自审）** | 放设计稿 + 指认定案 + 让**另一位**评审人下 approved |
| **评审闸门** | 卡进「待测试」 | 代码评审没有结论 | `studio_task_coding action=review status=approved` |
| **准出门禁** | 卡进「已完成」 | 清单没勾完 / 有失败用例 / 卡被标阻塞 / 没人签字 / **项目检查没跑或没通过** / **三层测试缺层（单元/集成/端到端，可用测试计划写「不适用 + 理由」）**；需求级另加**可执行用例占比 < 60%** | 逐项补齐；`override` 强推需写理由 |
| **合并门禁** | 合 MR | 评审未过 / 可执行用例没通过 / 项目检查没过 / 登记的分支与 commits 对不上 | 同上；通过后可让平台代合并 |
| **发布门禁** | 发布版本 | 有未完成卡 / 阻塞 / 未结缺陷 / 失败用例 / 没填 tag / 冒烟未过 / **没有审批记录** | 先「审批通过」再发布；确实要发走「强制发布」并写原因 |

**设计闸门与「设计评审通过」的区别**：评审通过 ≠ 定案。多稿时必须指认 `chosenId`，否则仍被拦——这是刻意的，防止「评审通过了但没人说清用哪一稿」。

## §5 AI 怎么用 {#ai}

### 5.1 先查再动（任何写操作之前）

```
studio_task_list（按项目/状态过滤）→ 找到卡
studio_task_get（读全量：需求、清单、用例、交付物、评论、历史）→ 再决定做什么
```

评论是**最新需求**。评论里说「等等」「先别动」，就停下汇报，不要改状态。

### 5.2 一条需求从零到能开工

```
studio_requirement_save {
  title, description,
  project,
  discovery: { server, auth, boundary },          // 三问，缺一项拆卡被拒
  points: [{ id:'p1', title, acceptance:[{id,text}] }]
}
studio_requirement_review { id, decision:'submit' }   // 提交评审
studio_requirement_review { id, decision:'approve', by } // 通过（人或有权限的角色）
studio_requirement_split { id }                        // 一个功能点一张卡，返回 created + warnings
```

`warnings` 别丢：说了「有服务端」却没有一条后端功能点、说「没服务端」却要动接口、功能点太空 —— 都是要回头补需求的信号。

**拆卡闸门（默认开）**：每个功能点至少要有一条可判定的验收条件（输入/操作 + 可观察结果），否则 `studio_requirement_split` 会拒绝并点名是哪个功能点。这是产品这一棒的质量底线——没有验收条件的卡，研发只能猜、测试只能编。

### 5.2.1 四棒各交什么（派单提示词会按卡所在列自动注入）

| 角色 | 交什么 | 不交会怎样 |
| --- | --- | --- |
| 产品经理（澄清） | 六段需求说明（背景/目标/范围/不做/验收/风险）、澄清三问与待确认问题、功能点 + **可判定验收条件** | 拆卡被拒；研发/测试没有验收口径 |
| 架构师（方案） | 方案要素（改动边界/数据模型/接口契约/失败回滚/并发幂等/性能容量/兼容灰度/备选）、**每条验收条件用哪条测试线验**、给研发的改动清单与自验步骤；**设计评审不能自审**（稿子的作者或面板「人」以外的人来下 approved） | 设计闸门拦在「开发中」之前；研发按猜的实现 |
| 开发工程师（待开发/开发中） | 改动映射（验收条件 → 文件 → 验证方式）、分层自测命令与结果、`studio_task_coding` 执行记录、交付物、给评审的交接契约 | 准出/评审拦；改动无法审计 |
| 测试工程师（待测试） | 三层测试（单元/集成/端到端）用例与执行结果、测试计划（哪层不适用 + 理由）、测试报告 | 三层闸门拦在「已完成」之前 |

四棒共用**协作约定**：先读上游交接契约与交付物；上游「未决」逐条回应（解决/接受风险/驳回+理由）；给下一棒三句话（要他做什么/不要做什么/风险点）；需要谁配合就 @谁，不替对方做他那一棒。卡抽屉「概览 → 协作链」能一眼看到四行各自的交付状态。

### 5.3 干完活要留的东西（缺一样都推不动）

```
studio_task_comment        { id, body }                 // 做什么、怎么做、验证了什么
studio_task_artifact       { id, kind, title, content } // 需求/设计/用例/报告…（正文会写进云盘）
studio_task_coding         { id, action:'update', agent, branch, commits, files, testsTotal, testsPassed }
studio_task_coding         { id, action:'review', status:'approved', reviewNote }
studio_task_case           { id, cases:[…] }            // 或者 studio_task_add_cases（可执行用例，会当场试跑）
studio_task_check          { id, itemId, note }         // 清单逐项勾，附证据
```

**改了什么代码、评审怎么说，卡上要看得见**（2026-11-24 起）：

- **代码改动**：抽屉「执行记录 → 代码改动（git diff）」直接读仓库（卡的 worktree，没有就用项目/服务的本机代码目录），用 BoardUI 树形视图按目录分组列改动文件（新增/修改/删除 + 每个文件 +N −M），点文件看逐行 patch，或切「全文」读工作树里的文件本体（带行号，200KB 上限）；可复制路径/内容，有关联 MR 时直接跳 GitLab 的 files；有提交历史时可切「某一次提交」，文件多时按路径筛。另给总增删行数与「还有 N 个文件没提交」的提醒。卡面同时有「代码 N 文件 +A −D」与「评审通过 / 评审要改」两个 chip，不点开卡片也能看出研发这一棒干了多少、评审过没过。
- **没登记也不会空着**：卡进「待评审」时，研发若没调 `studio_task_coding`，平台会从 worktree 的 `git log` / `git diff --numstat` 补一条执行记录（`agent = git 自动采集（研发没登记执行记录）`）并留一条评论；研发自报的字段一个都不覆盖，只补空着的部分。
- **评审意见进讨论区**：`studio_task_coding action=review`（agent 走工具）与面板上的「评审通过 / 要求修改」两条路都会**自动补一条评论**（`代码评审 · 通过（评审人）` + 意见正文），所以讨论区里一定看得到架构的意见；不再只躺在 `coding.review.note` 里。意见里 @ 开发工程师 仍会照常派单。每条评论右上角有「编辑 / 删除」：编辑就地改成 textarea 保存，删除先确认；改删都留历史。

| 需求 | `studio_requirement_list` `studio_requirement_get` `studio_requirement_save` `studio_requirement_review` `studio_requirement_split` `studio_requirement_signoff` `studio_requirement_folder` `studio_requirement_questions` `studio_requirement_comment` `studio_requirement_doc` `studio_requirement_requester` `studio_requirement_assist`（需求对话澄清，和模型聊；只读，与面板的「需求对话澄清」同一份实现） |
| 设计/交付物 | `studio_task_design` `studio_task_artifact` |
| 执行/评审 | `studio_task_coding` `studio_task_quality` `studio_merge_gate` |
| 测试 | `studio_task_case` `studio_task_add_cases` `studio_task_test_plan` `studio_task_generate_cases` `studio_test_run` `studio_test_suite` |

**三层测试（单元 / 集成 / 端到端）**：每条用例可带 `tier`（不写按断言推断：`browser` → 端到端、`http`/`db` → 集成、shell 里的单测命令 → 单元）。代码类卡的准出要求**每条线要么有可执行用例，要么用 `studio_task_test_plan` 写明「不适用 + 理由」**（`config.caseGate.tiers=false` 才关）；卡片抽屉「测试」页有三层进度条、每层的「跑这层 / 不适用」按钮和最近执行批次，卡片正面会显示「缺 单元/端到端」。测试专家的派单提示词会带上需求功能点与验收条件、当前三层的缺口和每层怎么落，缺层时要么补用例、要么写清为什么验不了。

用例列表本身是**紧凑卡片**：结果选择 / 标题 / 操作在顶部，接口定义、响应片段、执行步骤、功能点、记录默认**收起**，点「详情」才展开——35 条用例也能一屏扫完，不再被长接口和响应片段撑成一片。

用例区顶部有筛选 chip（全部 / 未跑 / 不通过 / 跳过 / 通过）与标题搜索，列表默认**失败在前**；三层测试进度与验收清单排在用例之后，测试页不再常驻评论框，执行回执会粘在列表顶部。点行内「改定义」会展开一张表单（接口 method/地址/状态码/包含文本，或 shell 命令 / 数据库文件与 SQL / 浏览器地址），改完一次保存；失败用例自动开的缺陷会用 `缺陷 BUG-xxx` chip 标在那一行。

**同名空壳用例原地升级**：`studio_task_add_cases` 碰到卡上已有同名草稿（只有标题，含「（可执行）」这类后缀差异）时，会把断言补到原用例上（保留 id / 功能点 / 验收条件），**不会新增一条重复**；同名且已可执行的跳过。以前会并存，导致「15 条里 7 条永远跑不了的草稿」，需求级可执行覆盖被拖到 53%。

### 5.5 常见错误与正确写法

| 想干的事 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 改状态 | 直接写库 / 伪造 `coding` 记录 | `studio_task_update`（会过门禁） |
| 拆卡 | 手工 `task_create` 一张张建，忘了挂 `pointId` | `studio_requirement_split`（自动挂点、清单继承验收条件） |
| 跑用例 | 自己判断「应该没问题」 | `studio_test_run`（平台真发请求，失败自动开缺陷卡；需求文档改版后，之前通过过、但最后一次执行早于文档更新的用例会标「需复跑」（矩阵 / 抽屉测试页 / 影响面都能看到，只标不改）） |
| 交付物 | 只在评论里说「已完成」 | `studio_task_artifact` 登记（正文进云盘，可被下一个人打开） |
| 遇到别人的卡 | 直接改别的专家的卡 | 评论里 `@专家名` 交给对方 |
| 不知道做什么 | 猜 | `studio_task_list` + `studio_task_get`，看不明白就问人 |

**不要绕过工具层走 HTTP**：工具层的入参会做白名单校验、回读落库结果、写审计。只有工具确实没覆盖的（例如 Drive 的批量操作）才走 HTTP，并在评论里说明原因。

### 5.6 先聊清楚再建卡（无卡会话）

「下个版本先做哪几张卡」「这个需求到底要不要做」——这类问题不该先建一张卡再等 5 秒 tick 派单。现在可以直接开会话：

- **面板**：设置 → 专家 / 专家团，每一行有「发起会话」；说一句想聊什么就开聊（团长接话）。
- **HTTP**：`POST /studio-api/agents/chat { expert 或 team, member?, topic, instruction?, workdir? }`（`expert` 既认专家 id 也认专家团 id；专家团默认团长接话，`member` 可以指定团里的某一位）。
- **工具**：`studio_session_start { expert, member?, topic, instruction?, workdir? }`，agent 自己也能发起。

会话会出现在 `GET /studio-api/agents` 的 `chats` 里（不占卡的派单槽位），要停就 `POST /agents/stop { sessionId }`（只 abort，transcript 留在侧栏）。会话 id 是 `studio-chat-<expert>-<hex>`：跑的是**对话模式**的提示词（不要开工、不改代码、不建卡、不往看板写评论），transcript 就是普通 DSH 会话，在侧栏按会话名接着聊。它不会污染看板，也不会冒充某张卡的消耗（成本页只把它算进总量与按专家）。聊到能落地时，请它给一段可直接复制的需求/卡描述（标题 + 背景 + 可判定的验收要点），再由人决定建不建。

**和「派单」的区别**：派单是 `POST /agents/run { id, expert?, instruction? }`，必须有卡、会把卡上的工位提示词一起注入、跑完要求登记评论并推进列。`expert` 传错时会分开报：卡不存在 / 目标不存在（或停用、团里没人）/ 这一列没人负责——不再一律回「这一列没人负责」。

**和「需求对话澄清」的区别**：需求澄清是和**模型**聊（面板的需求页，或 `POST /requirement/assist`、工具 `studio_requirement_assist`）——它只回一段文字、不写库，用来把一句模糊想法挖成可验收的需求或 PRD 草稿；无卡会话则是和**某位专家/某个团**聊，会真的建一个 DSH 会话、能读工作目录、能记住这几轮。前者便宜、一次性；后者贵、有上下文人设，适合「和这个人/这个团讨论」。两者都可以用来「想清楚再建卡」，按要不要人设与多轮记忆来选。

| 测试执行 | 允许接口/shell/浏览器/数据库用例、允许的域名、执行上限 | 想跑 shell 用例必须打开开关并配 `shellCwd` |
| 成本与预算 | 每个模型的价目表（元/百万 token）、预算 | 改了价目表，效能的成本数字才会变 |
| 部署环境 | 预发/生产环境记录 | 发布准入要求「上过预发」时要用 |
| 看板外观 | 标题、列宽、显示项 | 只影响展示 |
| 统一登录（LDAP） | 目录账号登录 | 连不上目录时切「本地超管」 |
| 权限与审计 | 成员、角色、访问级别、审计日志 | 破坏性操作都要 `confirm`；**项目/专家/团队配置、技能上传、合并 MR、灰度回滚、清库只有管理员能做**（成员写这些会被 403） |
| 数据与备份 | 快照、恢复、导出 CSV、清空 | **删数据前先做快照** |

**保存条**：页面级草稿（看板外观 / 自动派单）的保存条粘在面板底部，改了标「未保存」，切分区先确认；其余分区是**分区保存**（抽屉右下角 / 行内按钮）或**即时保存**（开关一拨就生效，例如权限名单、执行开关）——这是有意的：不同对象、不同权限，混成一个大草稿容易误保存。

设置页有**未保存提醒**：文本改过却没点保存时，页内会挂一条黄色提示；切到别的分区会先确认「丢弃并切换」。下拉/开关里有几项是即时保存的，不参与这个提醒。

## §8 排障手册 {#排障}

> 用法：搜「症状」那一列的关键词。

| 症状 | 先查 | 怎么修 |
| --- | --- | --- |
| 卡推不动，历史里写「被拦」 | 历史里的原因文案 | 按文案补齐（清单/用例/评审/设计/项目检查）；确实不适用才 `override` 写理由 |
| 看板顶部挂「设计闸门 已关闭」 | 设置 → 列的负责人 | 想有保护就点开；关着时推进会在历史留痕 |
| 设计批准被拒「设计不能自审」 | 稿子是谁放的、这次评审人是谁 | 自审不算评审：让**另一位**专家下 approved，或用面板以「人」的身份通过（`studio_task_design` 的 `by` 换成评审人）；被拒的提交不会落库 |
| 拆分卡被拒「先把澄清答完」 | 需求详情 → 澄清三问 | 答完三问再拆；三问要写清做什么/谁鉴权/交付边界 |
| 拆卡被拒「先过评审」 | 需求详情 → 评审 | 提交 → 通过再拆；已是 `active` 的需求可直接拆 |
| 交付物「同步到云盘」没出文档 | 抽屉交付物里 `doc.error` 的文字 | 见下三行 |
| 　· 错误里有 `unsafe file path` | lark-cli 只认当前工作目录子树 | 已修（0.9.44）：上传用 cwd + 相对文件名。升级即可 |
| 　· 错误里有 `larkJson is not a function` | 调用处漏传参数 | 已修（0.9.46）：`drive-sync` 四个函数有参数守卫，报错会点名 |
| 　· 错误里有 `unsafe`/`&`/`|` 被截断 | Windows 上 cmd.exe 把 `& \|` 当语法 | 已修（0.9.45）：参数逐个加引号 + `windowsVerbatimArguments` |
| 　· 错误里有 `parent node not exist` | 缓存的云盘文件夹 token 已经失效（文件夹在飞书被删了） | 0.10.1 起**自动自愈**：作废缓存 → 重建文件夹 → 重试一次。老版本请升级；临时应急可先把这条需求重新建一次文件夹（`studio_requirement_folder`） |
| 　· 错误里有 `--file must end with .md` | 交付物标题太长，文件名被截断时把 `.md` 一起截掉了 | 0.10.1 起 `artifactFileName()` **先截断再补后缀**；老版本临时把标题改短一点再同步 |
| 　· 错误里有 `unknown error` 且反复重试 | `doc.token` 指向的文件随文件夹一起被删了，`+overwrite` 必然失败 | 0.10.1 起覆盖失败会**降级成新建一份**并刷新 token；手动可在抽屉里对该交付物再点一次「同步到云盘」 |
| 交付物大量同步失败，想一次性补齐 | 哪些件没有 `doc.token` | 需求级：`POST /studio-api/requirement/sync {id}` 逐条跑（会自动重建失效文件夹）；零散件：`POST /studio-api/task/artifact/sync {id, artifactId}`。跑完看 `doc.token` 非空、`doc.error` 为空即成功 |
| 产物落在需求根目录而不是 `01 需求文档` | `doc.error` 是否为空 | 空 = 子目录已建好；非空按提示修。历史文档不会自动移动，新文档才进子目录 |
| 云盘根目录一堆同名文件夹 | `npm run drive:gc -- --base <端口>` | 先体检；`--apply` 才删（只删孤儿） |
| 侧栏同一个需求有多个同名工作区 | 设置 → 自动派单 →「工作区分组」 | 选「一个需求一个文件夹」后新派单会复用已有同名工作区；旧注册先 `node tools/workspace-dedupe.mjs --base http://<host>:18080` 看计划，再加 `--apply --yes` 清理（只删注册，会话日志保留）；旧的一卡一 worktree 文件夹加 `--legacy` 一起列 |
| 面板白屏 / 一行「渲染失败：xxx is not defined」 | 浏览器 console | 这是前端 `ReferenceError`；`node --check` 查不出，重启/升级后复现就报 issue |
| `curl`/脚本打 `/studio-api/*` 回 **401 `login_required`** | 是不是拿裸 curl 打的（或脚本没带 `STUDIO_TOKEN`） | 接口现在过宿主的信任栅栏：没有已认证的浏览器会话就 401。**脚本先换 cookie**：`curl -c jar.txt "http://<host>:<port>/?token=<启动 token>"`（303 + Set-Cookie），之后每个请求 `curl -b jar.txt …`。启动 token 这样取：`journalctl -u dsh-web -n 50 \| grep -o 'token=[^&]*' \| tail -1`（每次重启都会换）。源码检出里 `tools/lib/studio-auth.mjs` 封成了 `studioFetch()`，**npm 包里不带 `tools/`**。**探活别用 `/state`，用 `curl /studio-api/health`** |
| 打 `/studio-api/*` 回 **403 `bad_origin`** | 请求的 `Host` 是哪个、有没有带 `Origin` | 这是 Host/Origin 栅栏没过：用 `127.0.0.1` 或这台机器登记过的地址访问（回环永远可信）；反向代理没透传 `Host` 时也会命中这条 |
| 浏览器打开面板正常，但脚本/探针全 401 | 脚本有没有换 cookie | 浏览器靠 `?token=` 那条 URL 自动拿到 cookie，脚本没有；按上一条用启动 token 换。换不到会明确报「换不到会话 cookie（HTTP 401）」 |
| 改了代码重启没生效 | `npm run sync:profile` 的版本输出 | 确认 profile 版本 = 仓库版本；前端改动还要 `cd web && pnpm build` |
| 派单没反应/没留言 | 会话日志 `turn/end`、集成健康 | 常见是无可用模型通道（503）；先看「集成健康」 |
| 卡上写着「模型漂移…已归档并重建」，实际还在跑旧型号 / 报 `503 No available channel for model …` | 会话日志里的 `request/header.config.model`；`~/.dsh/sessions/*/<sessionId>` 到底在哪个目录 | 2026-11-25 之前 `guardModelDrift` 用**当前派单目录**找旧会话，卡换过目录（兜底目录 → 项目仓库）就 rename 扑空、重建没生效、评论还写着「已归档」。现在按「当前目录 → `sessionPersistence.location` → 扫 sessions 下每个 slug」定位并归档；**重建后仍不一致会让这一轮失败并挂阻塞**（写明旧/新型号），不会拿旧型号硬跑。手工修：删掉 `~/.dsh/sessions/<slug>/<sessionId>` 后点「马上处理」，或重启 dsh |
| 看板一直显示「处理中」，但「集成健康 → 派单运行状态」的 running 是空的 | 这张卡的 `dispatch`（`/state` 里看 `state/status/at`） | `state=running` 但会话早就没了（进程重启/会话崩）时，tick 每轮会按「真会话表优先、10 分钟超时兜底」判一次：挂死的印记自动收回（清 `status`、历史里写「派单印记已收回…」），下一轮重新派。历史里没有这句，说明还没超时或会话其实还活着 |
| 重启 dsh 后卡不自己接着跑 | 卡上的 `dispatch`（`state`/`resume`/`advanced`/`attempts`）与列是否勾了「自动派单」 | **进程结束时还在跑的卡**：`reconcile` 会清掉本列印记并打 `resume`，下一轮 tick 重派（**不受自动列勾选限制**，dev/review/accept 里的也派）。**上一轮正常结束但没换列**：`state=done, advanced=false`，重启后同样 `resume` 续跑。**人主动「停止」的**（`state=stopped`）不会自己跑，点「马上处理」。若历史里一条「重启续跑/abandoned」都没有，说明这张卡当时既不在跑、也没有未完成的印记——看下它是不是阻塞了 |
| 卡跑完停在原列不动 / 同一个 agent 反复自己跑 | 这张卡的 `dispatch` 与设置 → 自动派单 | 正常跑完没换列的卡：`state=done, advanced=false`，平台按 `retry.baseMs` 冷却后**自动再派一次**，最多 `retry.max + 1` 轮；用完挂阻塞并写「AI 连续 N 轮没有推进」。嫌吵就把那一列从自动派单里去掉，或把 `retry.max` 调小；想让它别停就点「马上处理」人工补一句指令 |
| 人工签完字，卡上还写着「阻塞」 | 卡上的 `blocked`（`by` / `until` / `reason`） | 2026-11-26 起支持**条件型阻塞**：agent 用 `until` 说明在等什么（`human-signoff` 等人工签字 / `sub-cards-done` 等子卡收口），条件满足由 tick **自动解除**并写「系统自动解除阻塞」历史，不用人再点；人亲手挂的阻塞（`by` 是人名）仍要人点「解除」。老数据没有 `until` 的会按 reason 关键字补判一次 |

## §8.1 只对脚本 / 工具开放的能力（面板里没有按钮，不是坏了）

有些接口是给自动化用的，故意不做界面 —— 免得每个能力都往单文件产物里塞一份 UI。
找不到入口时先看这张表，别当成 bug：

| 能力 | 怎么用 | 为什么没做界面 |
| --- | --- | --- |
| 为什么我被拒了 | `POST /studio-api/access/explain {route, method}` | 排障用，人看的是面板上的报错文案 |
| 可用模型清单 | `GET /studio-api/models` | 专家的模型目前是自由填写的字符串，接成下拉要等模型路由定稿 |
| 事件账本回查 | `GET /studio-api/events?since=<seq>&limit=100` | 给 webhook 消费方对账用；面板看的是卡片流转 |
| 派单日志导出 | `GET /studio-api/export/dispatch.csv`（仅本机） | 内容是操作人姓名，按敏感导出处理 |
| 审计导出 | `GET /studio-api/audit/export.csv`（仅本机） | 同上 |
| 探活某个模型通道 | `POST /studio-api/agents/probe` | 派单失败时由巡检脚本调用 |
| 把订阅的会话从工作区摘掉 | `POST /studio-api/workspace/detach` | 管理动作用 `tools/workspace-dedupe.mjs` 走 |
| 核对自报的代码事实（自动采集） | `POST /studio-api/task/verify-coding {id}` | 与面板的「核对代码事实」不同：那条是**对账**（`/task/coding/verify`，人看报告），这条是**采集**（把 worktree 的 git 事实补成一条执行记录）。卡进「待评审」时平台会自动跑一次，所以没有按钮 |
| 用例套件清单 | `GET /studio-api/suite/list` | 面板的套件区读的是 `/cases`（一次带 suites + counts）；这个接口留给脚本单独列套件 |
| 列出 / 删除工作区 | `GET /studio-api/workspace/list`、`POST /studio-api/workspace/delete` | 管理工作区用 `tools/workspace-dedupe.mjs`；面板不提供删除（删错会把整棵会话树挪走） |
| 多维表格镜像 | 面板已有按钮（设置 → 飞书机器人）；接口 `POST /studio-api/feishu/mirror` | — |
| 需求带进度的一览 | `GET /studio-api/requirements` | 面板用的是 `/state` 里的需求 + 抽屉里的矩阵；这个接口留给脚本 |
| 只读一份集成健康 | `GET /studio-api/integrations/health` | 与 `/state` 的 `integrations` 同一份 `healthReport()`，给监控脚本用（省掉整包） |

> 这几条**保留**而不是删掉：都是只读、成本极低，删了对写脚本的人是破坏性变更。
> 找不到按钮时先看本表，别当成 bug —— 真正的坑是「接口没有、面板也没有」。

## §9 日常运维

| 场景 | 命令 |
| --- | --- |
| 面板渲染体检（改前端后必跑） | `npm run probe:panel -- --base http://127.0.0.1:<端口>` |
| 看某张**真卡**的代码改动（逐文件 diff） | `STUDIO_DIFF_CARD=<标题片段> npm run probe:panel -- --base <端口>`：探针会打开那张卡 → 执行记录 → 代码改动，断言「分支 ← 基线」、文件数与逐行 patch，并截图 `tmp/probe/drawer-diff-real.png`；目标机开了登录时再加 `STUDIO_TOKEN=<会话令牌>`（登录返回的 token，或浏览器 `dsh-auth-*` cookie 的值） |
| README 截图重拍 | `npm run shots -- --base http://127.0.0.1:<端口>` |
| 云盘孤儿目录体检 / 清理 | `npm run drive:gc -- --base <端口>` / 加 `--apply` |
| 会话归档目录清理（`~/.dsh/sessions-archive`，只删 `*.stale-<时间戳>`） | `npm run gc:archive`（预览）→ `npm run gc:archive -- --apply`；`--days 7 --keep 50` 可调保留窗口 |
| `.agents/worktrees` 残留目录体检 / 清理 | `npm run worktree:gc`（只体检）/ 加 `--apply` 真删 / `--strict` 有孤儿退出 1；`--days N` 调老化门槛（默认 7 天）。判据只有一条：**不在 `git worktree list` 里**就是孤儿，不按目录名猜。Windows 上删之前会先摘掉 `node_modules` 联接（否则会顺着联接删主仓库依赖） |
| 执行播报写哪儿 | 设置 → 自动派单 → 「执行播报」：`feed`（默认，卡上「执行记录 → 执行播报」）/ `comment`（写成评论，旧行为）/ `off` |
| 派单会话目录体检 / 清理幽灵卡 | `npm run gc:sessions`（预览）/ 加 `--apply` 才删。判据是「卡已不在台账里」，先看预览再删 |
| 平台全闭环自检 | `STUDIO_BASE=… node tools/e2e-loop.mjs --k 3`（跑完自删） |
| 真库能不能起 | `npm run smoke:store -- ~/.dsh/dsh-studio.db` |
| 发版前文档一致性 | `npm run release:check` |
| 发版后核对（tag/npm/Release） | `npm run verify:release` |
| CI 结论 | `npm run ci:watch`（失败会自动贴日志尾巴） |

**备份**：改数据前在「设置 → 数据与备份」做快照；手工备份就是拷 `~/.dsh/dsh-studio.db`（连同 `-wal`/`-shm`）。

## §10 术语表

| 词 | 意思 |
| --- | --- |
| 功能点 Point | 需求里可验收的最小单位；拆卡时一个功能点变一张卡 |
| 验收条件 Acceptance | 功能点下的一句话断言；**卡的验收清单就是它** |
| 卡 Task | 能派单的工作单元；一行一个列状态 |
| 门禁 Gate | 推进前必须满足的条件；拦住时卡留在原列并写历史 |
| 闸门 Gate（可关） | 设计闸门 / 评审闸门，可在设置里关，关着时推进留痕 |
| override | 绕过准出的显式记录（必须写理由，计入统计） |
| 合并门禁 | 合并 MR 前的证据检查（评审/用例/项目检查/代码事实） |
| 准出门禁 | 进「已完成」前的检查（清单/用例/阻塞/签字/项目检查） |
| 派单 | 把卡交给某个专家会话去干活（`/agents/run`） |
| 停摆 | 卡在某一列但长时间没有派单/动作，工作台会标出来 |
| 交付物 Artifact | 卡上的产出物（文档/MR/用例集/报告），正文进云盘 |
| 技能 Skill | 可复用的做法，派单时注入给专家 |
| 隔离（worktree） | 每张卡的派单在独立 git worktree 里干活，互不干扰 |

## 附：给 AI 的三条硬规矩

1. **先读再动**：`task_get` 读全量（含评论与历史）再决定；评论是最新需求。
2. **干完留证据**：评论 + 交付物 + 执行记录 + 用例 + 清单，缺一样都推不动门禁。
3. **不要伪造**：不直接写库、不手填 `coding`、不替别人签字；做不到就 `block` 并写清原因。
